## 改了什么

G7 主体是验收，但验收过程发现并修复了两个真实缺陷（先复现、定根因、再修复）：

### 1. ConceptRef `key` 计算字段导致 journal 重放数据丢失（严重）

- 现象：`ConceptJudgment` 写入 journal 后，进程重启再读回时，含判断的事务被当作
  损坏尾静默截断（或中段损坏导致整本 journal 拒写）。
- 根因：`ConceptRef.key` 是 `@computed_field`，`model_dump` 时序列化进 journal 行；
  读取侧 `StrictModel`（extra=forbid）把多余的 `key` 判为非法。
  全量 1686 测试未暴露：journal 测试在进程内运行、状态有缓存，从不跨进程重放。
- 发现路径：§17.3 性能演练（冷读全量重放）→ 视图异常；随后在恢复演练复现。
- 修复：`backend/app/agents/student_model/evaluation/schema.py` 的 `ConceptRef`
  增加 `model_validator(mode="before")` 读回时丢弃 `key`（由四元组重算）。
- 回归测试：`backend/tests/test_evidence_journal.py::test_concept_judgment_survives_reload`
  ——先 append 含 judgment 的事务并断言原始 journal 行确有 `"key"`，再失效缓存、
  重新加载，断言 sources/judgments/concept_current 完整，且 API dump 仍带 `key`。
- 修复后全套后端回归重新跑过（见测试证据）。

### 2. 迁移 kind 误映射：旧 chat 作答 → DIALOGUE 应为 ASSESSMENT

- 现象：demo 账号浏览器验收时 `/assessment` 最近习题为空。
- 根因：现行 chat 题卡作答是 attempt 制观察（§11.4），走 `kind=ASSESSMENT`；
  `/quiz/recent` 与错题本投影只认 ASSESSMENT。迁移初版把旧 `chat` 记录映射成
  DIALOGUE，迁移作答因此从两个投影里消失。
- 修复：`scripts/migrate_learning_evidence.py` 的 `build_record_ops` 改为
  `kind=ASSESSMENT`（DIALOGUE 留给无任务的对话观察），并在注释中写明理由。
- 补救：核对 g6_apply manifest 确认 journal 自 apply 后未漂移 → 按清单回滚 →
  以修正后的映射对三个账号重新 apply（demo 7 sources / student_default 10 /
  usr_b0f55b21ca 0，全部 assessment-kind）→ verify → cleanup-legacy → verify 全绿。
  G6.md 的迁移语义段已补记这次纠正。

### 3. 迁移后长驻服务的状态缓存提示（运维注记）

浏览器复核时 `/quiz/recent` 仍为空——不是迁移问题：journal 状态在服务进程内
缓存，外部重写文件后不会自动失效。重启 backend 后投影立即正确。已在迁移 CLI
apply 输出末尾加 NOTE 提示（apply/rollback 后须重启在线服务）。

## 未运行项（如实记录，不得写成已过）

- **§18.4 教育审核 gold set：NOT RUN。** 需两名人类标注者对 P1–P4 输出标注
  一致率，无法在无人参与下伪造或代办；质量结论保持「未验证」。

## 已知支持范围与限制

- 评价质量（判分、主张措辞）未经人类 gold set 校准，仅工程链路与单元/故障
  注入测试覆盖；上线前应补 §18.4。
- 无 live LLM 执行证据前，性能数字代表 fake provider 下的服务端开销，不含
  真实模型延迟。
- 手写/图片作答解析未在本关验收范围（沿用 plan §20 的缩小口径：明确未观察）。
- 迁移是离线操作：apply/rollback 后必须重启在线服务（进程内状态缓存）。
